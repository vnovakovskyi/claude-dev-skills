# The knowledge base

Every dev-skills skill reads and writes one knowledge base. It holds what was
researched, planned, and learned, so that work on one service knows what was
already found or fixed in another.

Skills reach this file as `../../references/knowledge-base.md` from their own
base directory, and the index script as `../../scripts/reindex.sh`.

## Where it lives

The knowledge base is the `docs/` folder of the **folder Claude was started
in** (the session's first working directory), never a folder inside the
repository you work on. Call it the docs root below.

- When the folder Claude was started in is not inside a git repository (a folder
  that holds several repositories), nothing else is needed.
- When it is inside a git repository, add the line `docs/` to that repository's
  local exclude file, whose path `git rev-parse --git-path info/exclude` prints,
  if the line is not there yet. Do this before the first write, and tell the
  user once. The exclude file is personal and never committed. Never edit a
  `.gitignore`.

## Layout

```text
docs/
  INDEX.md                        generated by reindex.sh — never edit by hand
  .active                         the slug of the case in progress (one line)
  .approved                       written by the user only, for phase-gate
  codebase/<topic>.md             how existing code works (research-codebase)
  cases/<YYYY-MM-DD>-<slug>/
    case.md                       the card: the knowledge, kept short
    research.md                   the first research round
    research-<YYYY-MM-DD>-<subject>.md   a later round
    plan.md                       the first plan
    plan-<YYYY-MM-DD>-<subject>.md       a later plan
    architecture.md               optional
    data-model.md                 optional
    handoff-<YYYY-MM-DD>-<subject>.md    optional, state for a later session
    <anything else>               queries, logs, samples the case needs
```

## A case is a subject, not a ticket

One case holds one problem, change, or question, with everything done about it.

- **Reuse before you create.** When the request is about the same problem as an
  existing case — the same error, the same migration, the same component —
  continue that case: add a research round, a plan, a service. The same error
  showing up in another service is the same case.
- **Create** a case only when nothing in the index covers the subject. The slug
  is `<YYYY-MM-DD>-<ticket if any>-<short-kebab-subject>`, dated the day the
  case is created, for example `2026-07-08-orders-by-id-n1` or
  `2026-06-25-ABC-123-base-image-upgrade`.

## case.md

The card is what other skills read when they search, so keep it under about 60
lines and put details in the other files.

```md
---
title: GET /orders/{id} N+1 per line item in order-service
kind: incident
status: in-review
summary: N+1 per line item made GET /orders/{id} time out callers; item loading batched
repos: [order-service]
services: [order-service, billing-service]
tickets: []
prs: [org/order-service#123]
symptoms: ["Read timed out", "Broken pipe"]
related: [cases/2026-06-30-order-service-session-lookup]
created: 2026-07-08
updated: 2026-07-08
---

# GET /orders/{id} N+1 per line item in order-service

## Problem
What was observed, where, and how bad. Quote error texts exactly.

## Findings
The few facts that matter, with sources. Details: research.md.

## Decision
What was chosen and why, in a few lines. Details: plan.md.

## Outcome
What was done, where (PRs, commits, deploys), and what is left.

## Lessons
How to recognize this next time, and what worked or did not.
```

Frontmatter rules, so that `reindex.sh` and `grep` can read it:

- One `key: value` per line. Lists are inline: `[a, b]`. Quote list items that
  contain commas or brackets.
- `kind`: `incident`, `error`, `logs`, `upgrade`, `feature`, `review`, `infra`,
  or `question`.
- `status`:
  - `open` — being researched or planned;
  - `in-progress` — being implemented;
  - `in-review` — a pull request is open;
  - `solved` — the fix or change is merged or deployed;
  - `wont-fix` — decided not to act;
  - `abandoned` — stopped without a decision.
- `summary`: one line, under about 250 characters, that says what the problem
  is and, once known, how it ended. It is the line in the index, and the index
  is read in full, so keep it tight.
- `symptoms`: exact error messages, log lines, or alert names, copied, not
  paraphrased. They are the best search key across services.
- `updated` changes whenever the card does.

## codebase/<topic>.md

Notes from `research-codebase` carry a frontmatter too, so they appear in the
index:

```md
---
title: Web framework major upgrade
kind: codebase
repos: [api, shared-lib]
summary: what the framework's next major version touches in api and shared-lib, and in what order
updated: 2026-10-15
---
```

## Search before you work

Every skill starts here, before it reads code or writes anything:

1. Read `docs/INDEX.md` in full. It is one line per entry. If it is missing but
   `docs/cases/` or `docs/codebase/` exists, run `reindex.sh` first.
2. Search the cards and notes for the request's keys: exact error texts,
   service and repository names, ticket ids, library names. For example:
   `grep -rliF "<error text>" docs/cases/*/case.md docs/codebase/`.
3. Open the cards that match. Open a case's other files only when the card is
   not enough.
4. For a matching case in `in-review`, check its pull requests
   (`gh pr view <pr> --json state`). When they are merged, set the card to
   `solved`, update `Outcome`, and reindex.
5. Say what you found in one place of your output, with paths, under "Prior
   work". Say "none found" when there is nothing.

## After you write

- Set `updated` on the card you changed.
- Run `bash <plugin>/scripts/reindex.sh <docs root>`, where `<plugin>` is two
  levels above the skill's base directory. It rebuilds `docs/INDEX.md` from the
  frontmatter and prints a warning for every card with a missing field; fix
  those.

## What never goes into the knowledge base

Secrets, tokens, passwords, and personal data from logs or databases. Quote an
error text, not the token or the user it carried.
